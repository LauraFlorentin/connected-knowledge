# Make saved knowledge easy to use

Apply this completion standard to assistant-guided saves and note development.
Reuse the actual vault guide, source selection and write scope. It does not turn
a collector, importer, hook or private selected-save tool into an automatic
synthesis or attachment-fetching service.

## One clear entry point

Search existing maps, project notes and source identities first. Add the capture
to the most useful existing entry point. When several related sources need a
reading path and none exists, create one concise map under the vault's conventions.
A small standalone source can be its own entry point; do not create a map, project
entity or folder for every chat.

The first visible content should explain what the note is about and offer a few
descriptive links: read the source, see the decisions, inspect current progress,
or open a related idea. Put the short summary before detailed evidence. Preserve
required metadata and source IDs, but keep technical paths, hashes and message
indexes out of the introductory prose. Preserve the original messages separately;
a summary is not the transcript.

For long reviews, keep detailed evidence in linked source notes or a collapsed
Obsidian callout. Do not hide unresolved uncertainty needed to understand the
summary. Existing user prose and review status still require normal preservation.

## Connect the documents, not just their mentions

1. Identify the directly relevant documents attached or named in the selected
   material. Check whether their inclusion is within the task's authorized source
   and destination scope. A mention does not authorize recursively reading or
   copying other folders, accounts, repositories or every linked document.
2. For scoped, accessible documents, inspect enough to establish identity,
   version and relevance. Distinguish a file-existence check from a content review.
   Record missing or out-of-scope documents plainly; do not fabricate targets.
3. Reuse an existing source/reference note when it represents the same source.
   Otherwise create a short source/reference note when it makes the document
   useful to navigate, cite or connect. Link it from the summary or existing map,
   and explain the relationship. A filename in a transcript, code block, property
   or external URL alone is not a document node in Obsidian's graph.
4. A reference note may point to an original outside the vault. Label where it
   opens and any device limitation. Do not move or duplicate an authoritative
   editable register, inventory or project document just to make a graph node.
5. When document preservation is in scope, copy a PDF or selected attachment
   byte-for-byte to the existing attachment location, record its original locator,
   capture/version date and hash, and link it through the reference note. Embed
   supported PDFs when helpful. An embedded vault copy is a dated snapshot unless
   an actual synchronization process is configured and verified.
6. Compare versions before copying again. Unchanged bytes reuse the existing
   attachment; changed bytes are an explicit revision. Distinguish a later
   document version from the historical conversation that mentioned it. Never
   silently replace preserved historical evidence with a newer file.

Use the established source properties. A long archive ID belongs in identity
metadata or the capture index; preserve stable existing filenames. Prefer readable
display titles and labels rather than asking the user to navigate identifiers.

## Links that work in Obsidian

Use actual internal links between notes, including reference notes for external
documents. Obsidian's graph draws file links; relationship explanations remain
text unless a separate tool interprets them. Raw PDF nodes can depend on the
graph's Attachments filter; the reference note provides a normal note node.

Inside Markdown tables, prefer standard Markdown links with encoded spaces and
paths relative to the containing note. An unescaped alias pipe in a wikilink
splits a table cell. If using an escaped wikilink alias instead, verify it in the
target renderer; a structural checker may not understand every escaped form.
Outside tables, ordinary wikilinks with descriptive aliases are appropriate.
Check PDF page targets against the inspected document.

## Finish with a usable result

Read back the saved notes and originals, verify source hashes where recorded,
and check affected links with the vault's actual profile. When Obsidian UI access
is available, open the entry point in reading view, follow an important document
link, check a PDF embed if used, and inspect the local graph when graph connections
are part of the task. Collapse Properties in the current view when it obscures
the reading path; do not change global settings or install plugins merely for
presentation. Leave the useful entry point open.

If UI access is unavailable, finish the authorized file work and distinguish
structural checks from unverified in-app display. A zero-error checker result
does not prove usable layout or working app navigation.

Return one primary starting link, a short description of connected material and
its actual location, and any source or device limits. Separate captured, reviewed,
and promoted states. Preserve existing categories, status vocabulary and stable
records; links alone do not certify decisions or current implementation.

## Behavior checks for this instruction

- A chat and an authorized PDF produce a readable entry point, a linked document
  note and a clearly labeled PDF snapshot or original pointer, not only a raw path.
- A repeat save reuses identities, entry points and unchanged attachments.
- A newer document does not rewrite what an older conversation established.
- A missing or out-of-scope attachment remains a stated gap.
- A table's document link opens in Obsidian; its display label is not broken into
  separate cells.
- A raw capture-only tool run is reported as capture-only until the assistant
  actually performs the review and navigation work.
